# Whip MCP review

## Executive summary

**Whip has a strong MCP execution and permission foundation, but an incomplete integration-management experience and several concrete boundary bugs.**

The most important conclusion is **not** “replace our MCP system with Executor.” It is:

> Keep Whip’s daemon ownership, durable execution, exact-value handling, and definition-bound permissions. Fix the configuration and transport boundary bugs, then borrow Executor’s progressive discovery and integration-management UX.

### Main findings

- **Nine distinct issues were reproduced in isolated probes**, including:
  - HTTP credentials leaking across redirects.
  - Managed stdio processes receiving secret references literally.
  - SDK `servers: []` becoming unrestricted.
  - Session attachment widening a definition’s server selection.
  - Untrusted definitions executing startup commands before tool-call consent.
  - Incomplete tool pagination and reconnect behavior.
- **The model-facing architecture is already code-first.** Whip does not need Executor’s fundamental “execute code instead of loading thousands of tool schemas” transformation—it already follows that approach.
- **The TypeScript SDK can manage MCP through typed generic operations**, but lacks a first-class MCP service, catalog APIs, and a coherent integration authoring/testing story.
- **Web and desktop offer useful operational controls, not a complete MCP onboarding experience.**
- **The TUI is functional for status and intervention**, but the standalone CLI has substantially more setup functionality.
- **Executor is significantly ahead in discovery, credentials/accounts, tool inspection, and policy management.** Its approval defaults and execution semantics, however, are not appropriate replacements for Whip’s.

# 1. How Whip’s MCP system works

## 1.1 There are three different integration paths

These are easy to conflate, especially because our SDK also uses the name `Executor`.

### A. Whip consumes an external MCP server

```text
Model
  → rlm_exec
    → mcp host module
      → daemon/runtime services
        → capability + consent checks
          → root-owned MCP manager
            → stdio process or Streamable HTTP server
```

This is the primary MCP integration for Whip agents.

### B. Whip exposes built-in tools as an MCP server

```text
External MCP client
  → whip mcp serve, over stdio
    → daemon tool-host session
      → read / bash / edit / write
```

This is a deliberately narrower bridge. It does **not** export the full Whip agent runtime or aggregate configured MCP servers.

### C. A TypeScript application supplies tools and hooks to Whip

```text
TypeScript SDK
  → client.agents.serve(definition)
    → Whip definition registration + executor lease
      → tool.invoke / hook notifications
        → TypeScript handler
          → tool.result / hook.result
```

This uses **Whip’s daemon protocol, not MCP**.

**Implication:** an SDK-authored tool does not automatically become an MCP server tool, and attaching an MCP server does not generate TypeScript SDK handlers.

Sources: `internal/rlm/modules.go:23–36`; `internal/daemon/recursive_runtime.go:1618–1679`; `internal/mcp/serve.go:21–56`; `packages/sdk/src/agents.ts:218–330`.

---

## 1.2 The daemon owns MCP connections

Each root owns an MCP manager. Children resolve the root’s current manager rather than owning independent copies.

The manager:

- Discovers and normalizes server definitions.
- Starts enabled servers.
- Connects and initializes the MCP session.
- Retrieves the tool catalog and server instructions.
- Tracks connection state and catalog generations.
- Validates and dispatches calls.
- Handles catalog changes, reconnect requests, disabling, retirement, and shutdown.

Production stdio servers run through the daemon’s `ProcessManager`. Remote servers use the Go MCP SDK’s Streamable HTTP transport.

The basic status vocabulary is:

- `disabled`
- `connecting`
- `ready`
- `failed`

Those states do **not** independently express authentication, consent, or agent authorization. “Ready” means connected with a catalog, not “every agent can invoke every tool.”

Sources: `internal/daemon/daemon.go:274–286`; `internal/daemon/mcp.go:16–44`; `internal/mcp/manager.go:30–72, 360–433`.

# 2. How MCP servers are configured

## 2.1 Native configuration

Whip’s native configuration is in `~/.whip/config.json`, with an `mcp` map.

An illustrative configuration:

```jsonc
{
  "mcp": {
    "local-docs": {
      "command": ["/absolute/path/to/docs-mcp"],
      "env": {
        "DOCS_TOKEN": "$DOCS_TOKEN"
      },
      "enabled": true
    },
    "remote-docs": {
      "url": "https://example.com/mcp",
      "headers": {
        "Authorization": "Bearer $DOCS_TOKEN"
      },
      "startupTimeout": 30,
      "toolTimeout": 60
    }
  },
  "mcpImport": {
    "claude": { "enabled": false },
    "codex": { "enabled": false }
  }
}
```

**Important:** the stdio environment reference above illustrates the intended configuration contract. The current production managed-process path passes that reference literally; that is one of the reproduced bugs below.

Supported configuration includes:

- Command and arguments, environment, working directory.
- Remote URL and headers.
- Enabled state.
- Startup and tool-call timeouts.
- Provenance retained during import.

Default timeouts are 30 seconds for startup and 60 seconds per tool call.

Sources: `internal/config/config.go:164–171, 275–286`; `internal/mcp/config.go:31–51, 92–117`.

## 2.2 External discovery and precedence

The effective server definition is selected **whole-entry by name**, not field-merged.

Highest precedence first:

| Priority | Source |
|---|---|
| 1 | Whip’s own `mcp` map, including materialized imports |
| 2 | Codex configuration |
| 3 | `.mcp.json` in the root’s working directory |
| 4 | Global `~/.claude.json` |

The project lookup here is the working directory’s `.mcp.json`, not an ancestor-directory discovery walk.

Import policies support:

- Source enabled/disabled.
- An `only` name allowlist.
- An `exclude` denylist.

`exclude` wins. Filtered servers remain visible as blocked/disabled records rather than silently disappearing.

### A subtle default distinction

- **Fresh defaults explicitly disable Claude and Codex imports.**
- **An absent `mcpImport` block preserves legacy import-everything behavior.**

That distinction matters operationally and for security. A fresh installation should not be described as automatically executing repository MCP definitions.

Sources: `internal/mcp/config.go:170–181, 203–243, 275–343`; `internal/config/config.go:642–645`.

## 2.3 Live imports and materialized imports are different

There are two operations called “import” in practice:

1. **Live discovery:** read external definitions when constructing the manager.
2. **Materialization:** copy discovered definitions into Whip’s config using `whip mcp import`.

Materialization preserves references and provenance and does not overwrite existing Whip entries.

Consequences:

- Disabling a live import source does not remove definitions already materialized into Whip’s map.
- Removing a native override may reveal a lower-precedence imported definition again.
- Copying a definition into Whip’s file does not necessarily erase its imported/untrusted provenance.
- Foreign per-tool restrictions are not faithfully translated into Whip rules. Codex-specific approval subtables and tool restrictions are not equivalent to Whip policy.

This deserves explicit documentation and UI copy.

Sources: `cmd/whip/mcp.go:280–319`; `internal/mcp/codextoml.go:60–66, 188–190`.

## 2.4 Authentication today

Current authentication is primarily:

- Static headers.
- Environment references.
- Templates containing references.
- External `!command` secret helpers.

Remote header secrets are resolved at connection time. They are not refreshed per request.

**There is no native MCP OAuth lifecycle in the reviewed implementation:** no MCP authorization discovery, browser login, callback, token refresh, account selection, or reauthentication state machine.

Importing a server that works in Claude or Codex does not import that application’s OAuth token store.

Also, **legacy SSE transport is intentionally unsupported**. Streamable HTTP’s SSE notification stream is supported; these are different things.

Sources: `internal/mcp/manager.go:1044–1065`; `internal/config/secret.go:54–75, 261–265`; `internal/mcp/claude.go:56–66`.

# 3. How the model accesses MCP

## 3.1 A small code-facing surface

The model uses four host operations:

```javascript
await mcp.list_servers({});

await mcp.list_tools({
  server: "docs"
});

await mcp.instructions({
  server: "docs"
});

await mcp.call({
  server: "docs",
  tool: "search",
  arguments: { query: "deployment" }
});
```

Whip’s model does not receive one top-level provider tool for every remote MCP tool. Instead, it discovers tools from inside the runtime.

This is already the core context-efficiency principle behind Executor.

Current discovery returns:

- Server state, source, trust, and tool count.
- Tool names, descriptions, and input schemas.
- Definition identity and connection generation.
- An `authorized` indicator.

### “Authorized” is not “consent granted”

The flag reflects the agent’s capability grant. Invocation still needs current consent.

Similarly, discover-before-call is useful model guidance; the meaningful security boundary is the host’s dispatch-time validation, not the model’s willingness to follow a discovery recipe.

Sources: `internal/daemon/recursive_runtime.go:1624–1676`; `internal/rlm/guide_fragments.go:61–63`.

## 3.2 Permission architecture: a real strength

Whip checks two separate questions:

1. **May this agent invoke this exact tool?**
2. **Has the invocation been authorized under the current consent policy?**

Native configuration can satisfy consent. Imported and attached definitions generally require approval or a saved rule, subject to configured permission mode.

Important protections include:

- Server/tool/definition-specific selectors.
- Connection-generation binding.
- Full live ancestor-grant checks.
- Finite child grants rather than unrestricted inherited root authority.
- Revalidation after waiting for a server’s execution slot.
- Revocation and permission-policy changes checked before transmission.
- Retirement of queued and active admission contexts.
- No automatic replay of transmitted calls after uncertain failure.

Children snapshot the currently available, parent-authorized tool set. Later discoveries do not silently expand an existing child’s grant.

**These are meaningful protections worth preserving.** Executor’s nicer console should not distract from the sophistication already present here.

Sources: `internal/tools/mcp.go:81–178, 196–251`; `internal/mcp/manager_call.go:184–259`; `internal/daemon/mcp.go:65–116`; `internal/session/capability.go:230–338`.

## 3.3 Results are currently lossy

The result path is text-first:

- Text content is concatenated.
- Images/audio/binary resources become omission markers.
- Resource links become labels.
- `structuredContent` is retained only if there is no ordinary text output.

Thus a tool returning both a human summary and a machine-readable object loses the object. A screenshot-producing MCP tool does not deliver a usable screenshot through this path.

There are also no model-facing MCP `resources/read` or `prompts/get` operations.

This is an intentional implementation shortcut, not an accidental protocol crash—but it significantly limits interoperability and code-based composition.

Sources: `internal/mcp/manager.go:768–809`; `internal/rlm/modules.go:23–36`.

# 4. TypeScript SDK integration

## 4.1 What works today

The SDK exposes typed generic session operations, so MCP management is available:

```typescript
await session.query("mcp.status", {});

await session.command("mcp.reconnect", {
  name: "docs"
});

await session.command("mcp.disable", {
  name: "docs"
});

await session.invoke("mcp.attach", {
  servers: {
    docs: {
      url: "https://example.com/mcp"
    }
  }
});
```

The operation categories are useful:

- Queries read state.
- Commands mutate daemon-owned state.
- Ephemeral invocations carry sensitive one-shot input such as attachments.

The SDK also supports agent definitions with an MCP server selection.

However:

- There is no dedicated `session.mcp` facade.
- There are no equivalent public catalog/instructions/call management APIs for building a tool inspector or test panel.
- SDK authors do not get generated TypeScript bindings for discovered remote tools.
- The omission/empty-list contract currently has a serious normalization bug.

Sources: `packages/sdk/src/client.ts:64–74`; `packages/sdk/src/session.ts:14–21`; `internal/protocol/runtime_registry.go:63–68, 82`; `packages/sdk/src/agents.ts:111–112, 180`.

## 4.2 Recommended SDK direction

A small root-scoped MCP service would improve discoverability without changing architecture:

```typescript
// Proposed API shape—not implemented.
session.mcp.status();
session.mcp.reconnect(name);
session.mcp.disableForSession(name);
session.mcp.listTools({ server, cursor, limit });
session.mcp.describeTool({ server, tool });
```

Attachment semantics should be settled before naming a wrapper. Calling a destructive replacement operation `attach()` is misleading.

For richer management, add contracts in this order:

```text
Go protocol definition
  → generated protocol types/validators
    → SDK service
      → shared app and TUI
```

Do not add browser-side MCP connections or bypass the daemon with a second JSON-RPC client.

### Generated TypeScript: useful, but not the first prerequisite

Executor-style TypeScript descriptions would help models understand complex schemas. But first fix:

1. Correct server selection.
2. Complete and bounded discovery.
3. Preservation of structured results.

A beautiful generated return type is misleading if the runtime discards the structured return value.

# 5. Concrete implementation findings

Priority labels below are review priorities, not CVSS scores.

## 5.1 Fix promptly

### 1. Configured HTTP credentials leak across origins on redirects

**Reproduced.**

Whip injects configured headers in a `RoundTripper` on every request. Go’s normal redirect logic can strip `Authorization`, but the transport adds it back after that decision.

A two-server local test redirected between `127.0.0.1` and `localhost`; the destination received the fake bearer token configured for the original server.

**Fix:** bind configured credentials to the permitted origin. Reject or explicitly handle cross-origin and HTTPS-downgrade redirects. Cover custom secret headers as well as `Authorization`.

Source: `internal/mcp/manager.go:1051–1065, 1111–1115`.

### 2. SDK `servers: []` becomes unrestricted

**Reproduced against the compiled SDK; source matches.**

The authoritative definition semantics distinguish:

- `null`: all configured servers.
- `[]`: no servers.
- `["docs"]`: the named selection.

The SDK’s generic `list()` helper collapses both `undefined` and `[]` to `null`.

This means code calculating an empty allowlist can accidentally request all servers.

**Fix:** preserve explicit empty MCP lists specifically. Do not globally change the helper without checking other fields’ canonical semantics.

Sources: `packages/sdk/src/agents.ts:180, 211–213`; `internal/agentdef/definition.go:155–159`; `internal/agentdef/document.go:46–55`.

### 3. `mcp.attach` widens definition server selection

**Reproduced through the actual daemon/RLM call path.**

Startup filters manager configuration by the definition’s allowed server names. Attachment constructs a replacement from the supplied attachments plus **all native config**, without intersecting that selection.

The probe established:

1. A definition restricted to `local`.
2. Native `admin` absent from the initial manager.
3. `mcp.attach {}`.
4. An RLM call to excluded `admin/mutate`.
5. A counted effect occurred.

This was a fixture-level reproduction, not full SDK registration/startup E2E. It did exercise attachment, manager replacement, native trust, capability/consent checks, and the remote call.

**Fix:** centralize definition-aware selection across manager construction paths. If selection is intended as an authority boundary, represent it in authority rather than relying only on catalog filtering.

This is not an unauthenticated network exploit; it is unexpected widening through an authorized client operation.

Sources: `cmd/whip/daemon.go:177–195`; `internal/daemon/mcp.go:47–58`; `internal/daemon/definition.go:97–104`.

### 4. Managed stdio passes secret references literally

**Reproduced with a real managed child.**

The production managed transport copies `cfg.Env` into `ProcessManager` without resolving references. The fallback transport resolves them correctly.

A child configured with:

```text
REVIEW_DEST="$WHIP_REVIEW_TOKEN"
```

received the literal `$WHIP_REVIEW_TOKEN`, not the fake source value.

This is production-reachable, including through CLI diagnostics.

**Fix:** share point-of-use reference resolution between managed and fallback paths while retaining `ProcessManager` validation and safe environment handling.

Source: `internal/mcp/manager.go:386–433` versus `1074–1087`.

### 5. Tool-call consent does not protect startup execution

**Reproduced; exposure is conditional.**

Enabled imported/attached definitions are marked untrusted for calls but start eagerly.

Two probes demonstrated effects before tool admission:

- An untrusted stdio command created a temporary marker.
- An untrusted remote HTTP definition’s `!command` header helper created a marker during transport construction.

**Qualification:** fresh defaults disable imports. Exposure arises when a source is enabled, legacy configuration omits the import block, or an authorized client supplies an attachment.

The question is whether “enable Claude imports” should authorize arbitrary commands from every future project `.mcp.json`.

**Recommendation:** distinguish:

1. Permission to connect/spawn a server definition, including secret helpers and credential disclosure.
2. Permission for an agent to invoke its tools.

Bind startup approval to the definition. At minimum, document that tool consent is not a process sandbox.

Sources: `internal/mcp/manager.go:363–433, 1051–1059`; `internal/config/secret.go:64–75`; `internal/mcp/config.go:203–229, 262–269`.

## 5.2 Correctness and robustness

| Finding | Evidence | Recommended correction |
|---|---|---|
| **Only the first `tools/list` page is loaded**, at startup and refresh | Reproduced with a two-page server | Bounded all-pages discovery, cursor-cycle protection, atomic catalog publication |
| **Auto-reconnect stops after its first failed redial**, rather than exhausting the intended three attempts | Reproduced; existing test checks only an upper bound | Schedule subsequent eligible attempts; assert exact attempt count and intermediate-failure recovery |
| **Valid unrelated TOML can break all Codex discovery** | Reproduced with `[[unrelated.entries]]` | Compliant parser or genuinely isolated MCP extraction; surface parse errors |
| **Secret helper commands ignore caller cancellation** | Reproduced with an already-cancelled context and a one-second helper | Propagate startup/caller context and cap helper execution by the parent deadline |
| **Large discovery catalogs bypass bounded/handle-backed output** | Source-traced; oversized runtime probe not run | Paging/handles and an explicit total-byte budget |
| **Large MCP error content loses its handle and can exceed the worker frame limit** | Source-traced; oversized runtime probe not run | Structured bounded result/error envelopes; preserve inspectable evidence |

Sources: `internal/mcp/manager.go:142–177, 521–620`; `internal/mcp/manager_call.go:272–274, 313–326`; `internal/mcp/codextoml.go:31–49, 244–264`; `internal/rlm/quickjs_kernel.go:84–94`; `internal/rlm/protocol.go:44–51`.

Two particularly important details:

- The default worker frame is 1 MiB. A sufficiently large catalog/error can fail the cell rather than become a normal inspectable operation result.
- Normal daemon construction and materializing import do not consistently surface discovery parse errors. “No tools” can actually mean “configuration failed to parse.”

## 5.3 Test hygiene

`TestRealCodexConfigSmoke` reads the real home Codex configuration when present and can log header maps. It was explicitly skipped during this review.

**Recommendation:** make it opt-in and redact sensitive fields. A routine test suite should not opportunistically read and print developer configuration.

Source: `internal/mcp/realconfig_smoke_test.go:12–32`.

# 6. Is the web/desktop MCP experience good?

## Verdict

**Good operational scaffolding; not yet a complete MCP product experience.**

Web and desktop share the same renderer and MCP interface. Desktop does not currently add a separate native MCP setup experience.

## What is good

The shared interface provides:

- Server status, tool counts, source, notes, and errors.
- Reconnect/enable/disable.
- Claude/Codex live-import toggles.
- Offline, unsupported, loading, and retry handling.
- Periodic status refresh.
- Private one-shot JSON attachment input.
- Clearing attachment input before submission, without browser persistence.
- Bounded, keyboard-accessible approval details.
- Refresh-before-retry for uncertain approval outcomes.

These align well with daemon-owned work and avoiding accidental replay.

Sources: `packages/app/src/details/integrations.tsx:17–148`; `packages/app/src/details/shared.tsx:26–124`; `packages/app/src/requests.tsx:91–177`.

## Where it breaks down

### There is no complete setup journey

A user cannot complete this flow entirely in the UI:

```text
Add server
  → inspect definition
    → configure credentials
      → connect/authenticate
        → inspect tools
          → test safely
            → manage saved permissions
```

Missing pieces include persistent add/edit/remove, probe/preview, OAuth, account selection, import filters, and a real MCP catalog.

### “Available tools” is not an MCP catalog

That view calls `tool.schema`, which returns public built-in schemas.

A user sees an MCP tool count but cannot inspect the remote tool names, schemas, instructions, or authorization state.

**Immediate fix:** rename it “Built-in tools.”

**Next feature:** a read-only per-server catalog backed by daemon/SDK discovery.

Sources: `packages/app/src/details/integrations.tsx:273–308`; `internal/daemon/client_control.go:907–913`; `internal/tools/tools.go:495–499`.

### “Attach” actually replaces

The attachment operation replaces the manager using the new map plus native config. It does not merge old attachments or live imports.

A second small attachment can remove previously available nonnative servers.

**Minimum improvement:** explicit replacement language and an affected-server preview. Preserve the current private-input handling.

### Scope and outcome labels are ambiguous

These actions are not equivalent:

- Disable this server in the current session.
- Persist a host import setting.
- Request reconnect.
- Complete reconnect.
- Save a setting while reload remains pending.

The generic “Applied” message hides those distinctions.

Prefer explicit labels such as:

- “Disable for this session.”
- “Host import defaults.”
- “Reconnect requested.”
- “Saved; reload pending.”

### Remembered permission management is incomplete

Web offers host-wide remember, but the host-rule view is read-only. Session “Forget” does not revoke a host rule.

The remembered MCP selector is also exposed as opaque technical text rather than a clear explanation of the exact tool/server-definition scope.

**Fix:** readable scope, technical identity under disclosure, and a matching host-rule revoke path.

### State-specific controls need tightening

Blocked records can expose enable/reconnect buttons even though the live manager has no corresponding server. Every row gets broadly the same controls.

The UI should derive meaningful actions from actual state and advertised operation support.

### Accessibility needs targeted validation

Repeated action labels lack subject context in several places. Add names such as “Reconnect docs” rather than repeated “Reconnect.”

This is a source-supported improvement opportunity—not a claim that screen-reader testing failed. No live screen-reader audit was performed.

# 7. What about the TUI and CLI?

## TUI verdict

**Useful for experienced users; incomplete for onboarding and diagnosis.**

The TUI supports status/import/reconnect/enable/disable through `/mcp`.

Strengths:

- Concrete server state and source.
- Paged approval details for long MCP arguments.
- Readable remembered-permission wording: the exact tool and server definition in this tree.
- No accidental implication that the model can grant itself permission.

Gaps:

- No `/mcp add`, remove, attach, auth, or test flow.
- No browsable tool catalog.
- No dedicated live MCP management screen.
- The command palette derives names from local native config rather than daemon live/imported/attached/blocked inventory.
- No equivalent host-wide remember choice to the web interface.

The palette mismatch is especially problematic with remote daemons or session attachments: status can show a server that the palette cannot offer.

Sources: `internal/tui/client_parameters.go:79–102`; `internal/tui/client.go:1749–1773`; `internal/tui/permission.go:60–79`; `internal/tui/daemon_views.go:12–36`.

## CLI verdict

The standalone CLI is currently the best setup surface:

```text
whip mcp list
whip mcp add <name> -- <command...>
whip mcp add <name> --url <url>
whip mcp remove <name>
whip mcp import --dry-run
whip mcp import
whip mcp test <name>
whip mcp serve
```

But users should know:

- `list` is a merged configuration view, not a live health check.
- Add/remove persist configuration rather than directly updating every live root.
- A diagnostic connection test can execute startup commands and secret helpers.
- Removing an imported definition requires editing its source or changing import policy.

**Recommendation:** keep the CLI useful, but expose the same daemon-owned management semantics to the shared app and TUI instead of maintaining three different feature sets.

# 8. Whip versus Executor

## 8.1 They have different centers of gravity

| Dimension | Whip | Executor |
|---|---|---|
| Primary product | Durable agent runtime | Integration/catalog/credential broker |
| Consumes MCP | Yes | Yes |
| Serves MCP | Narrow built-in tool bridge | Central code-mode integration facade |
| Other integration protocols | SDK/native tool systems | MCP, OpenAPI, GraphQL, Google Discovery |
| Model discovery | Server list + whole-server tool list | Paginated lexical search + describe |
| Model code | Persistent runtime with checkpoints | Fresh QuickJS runtime per execution in local path |
| Typed guidance | JSON Schema | Generated TypeScript input/output descriptions |
| Credentials | Config/env/header/helpers | Integrations separated from owner/account connections; OAuth support |
| Approval | Agent grants plus consent | Policy engine; defaults derived partly from annotations |
| UI | Status/basic controls | Integration, account, tool, policy, run console |
| Numeric boundary | Lossless host codec | Ordinary JSON stringify/parse in reviewed QuickJS bridge |

Executor is MIT licensed.

## 8.2 What Executor does particularly well

### Progressive discovery

Executor’s funnel is:

```text
Compact integration inventory
  → tools.search(...)
    → tools.describe.tool(...)
      → exact tool invocation
```

Search supports query, namespace, limit, and offset, with explicit:

- `items`
- `total`
- `hasMore`
- `nextOffset`

Blank search without a namespace returns no arbitrary catalog dump. Blank search within an exact namespace supports exhaustive enumeration.

This is lexical ranking, not vector search. It still loads and ranks visible summaries in memory, so bounded output does not imply indexed server-side search.

**Borrow this design.** It would address Whip’s context and catalog-size weaknesses without replacing dispatch or permissions.

Executor source: `packages/core/execution/src/tool-invoker.ts:430–460, 657–737, 823–887`.

### Tool descriptions and result envelopes

Executor provides generated TypeScript descriptions and a discriminated result:

```typescript
{ ok: true, data: T, http?: ToolHttpMeta }
```

or:

```typescript
{ ok: false, error: ToolError }
```

That is substantially easier for model-written programs to compose than text scraping.

But **this is not semantic TypeScript checking**. Executor strips TypeScript syntax and dispatches through a lazy proxy. Runtime validation remains the real boundary.

Executor source: `packages/kernel/core/src/strip-types.ts:3–34`; `packages/kernel/runtime-quickjs/src/index.ts:228–251`; `packages/core/execution/src/tool-invoker.ts:25–39, 307–360`.

### Integration versus connection

Executor distinguishes:

- What the integration is.
- Which account/owner connection is used.
- Where credentials come from.
- Which policies apply.

That is a stronger foundation for multiple accounts and team use than a server name with headers attached.

For Whip, the first step need not be a generalized enterprise integration framework. Make credential ownership and the active connection explicit before adding more abstraction.

### Tool-management UX

Executor has:

- Probe-driven integration setup.
- Tool tree/detail views.
- Schemas and TypeScript previews.
- Account selection.
- Form/JSON arguments sharing one canonical state.
- Manual run.
- Policy editing and removal.

Borrow the workflows, not the Effect/Atom client architecture.

### Protocol regression discipline

Executor has implementation and tests for paginated discovery, catalog drift, stale sessions, owner-isolated credentials, OAuth refresh, safe stdio environment composition, and interrupted cleanup.

Its pagination loop has an overall deadline and a maximum page count—precisely the type of guard Whip needs.

Executor source: `packages/plugins/mcp/src/sdk/discover.ts:17–32, 56–119`.

## 8.3 What not to copy

### Annotation-derived default approval

Executor marks upstream MCP tools as requiring approval when `destructiveHint === true`. Missing that hint defaults toward approval unless explicit policy says otherwise.

A server’s annotation is not a sufficient basis for trusting an operation.

Whip’s definition-bound consent and agent grants are stronger boundaries.

### Model-resolved “approval” by default

Absent or unknown `elicitation_mode` selects model mode. In that mode, `resume` can receive accept/decline/cancel from the calling model.

Browser and native modes differ, but **default approval is not necessarily non-bypassable human approval**.

Do not transplant this into Whip.

Executor source: `packages/plugins/mcp/src/sdk/plugin.ts:539–548`; `packages/core/sdk/src/policies.ts:235–254`; `packages/hosts/mcp/src/browser-approval.ts:34–51`; `packages/hosts/mcp/src/tool-server.ts:1593–1642`.

### Stateless execution instead of checkpoints

Executor persists catalogs, credentials, policies, sessions, and related metadata. Its execution pause/resume uses live fibers and deferred responses.

That is not serialized guest-heap recovery. A Durable Object does not make arbitrary in-flight JavaScript checkpointed.

Whip should preserve its durable runtime model.

### Its QuickJS timeout algorithm without further investigation

**Source-supported hypothesis, not reproduced.**

Executor disables the guest interrupt deadline while host calls are in flight. A guest that starts an unawaited tool call and immediately enters an infinite loop appears able to block the host Promise callbacks needed to clear that state.

That could wedge the local in-process host despite the intended timeout.

This needs an isolated, externally killable reproduction before being treated as a confirmed vulnerability. It is nevertheless a reason not to reuse that algorithm.

Executor source: `packages/kernel/runtime-quickjs/src/index.ts:138–159, 324–343, 472`.

### Overclaiming network hardening

Executor includes useful hosted HTTP restrictions and redirect handling. However, DNS resolution checks depend on an optional resolver not supplied in the common scoped path reviewed.

It should not be described as comprehensively DNS-rebinding-proof based on that helper alone.

# 9. The outward `whip mcp serve` bridge needs a clearer contract

Today it advertises exactly:

- `read`
- `bash`
- `edit`
- `write`

It has:

- Stdio transport.
- No model loop.
- No imported MCP catalog re-export.
- No SDK custom-tool export.
- No resources/prompts surface.
- No HTTP listener requiring separate MCP network authentication.

The subtle issue is consent:

- The bridge installs a rejecting automation permission gate.
- It cannot obtain **new** consent.
- Existing applicable saved rules can preauthorize operations before that gate is reached.

Therefore:

> It is not correct to say all side effects are always denied. It is correct to say the bridge cannot obtain new consent.

An outer harness approving an MCP invocation is not currently forwarded as Whip consent.

**Recommendation:** document this explicitly. If the bridge should be more useful, add a deliberate trusted approval channel—not “an MCP call means approved.”

Whether this bridge should become an Executor-like aggregate is a product decision, not an obvious missing feature.

Sources: `cmd/whip/mcp.go:145–179`; `internal/daemon/tool_runner.go:53–57`; `internal/tools/tools.go:516–524`.

# 10. Recommended improvement sequence

## Phase 1 — Repair existing contracts

No broad redesign.

1. Scope HTTP credentials to origin.
2. Preserve SDK empty server selections.
3. Enforce definition selection across attachment/reconstruction.
4. Resolve managed stdio secret references correctly.
5. Make startup trust explicit.
6. Implement complete bounded pagination.
7. Fix reconnect chaining.
8. Make secret helpers cancellable.
9. Fix Codex parsing and diagnostic propagation.
10. Preserve bounded evidence for application errors.

Add focused regression tests alongside each fix. The current strong admission tests should remain intact.

## Phase 2 — Make the existing product truthful

Small, high-value UI work:

- Rename “Available tools” to “Built-in tools.”
- Clarify replacement attachment semantics.
- Distinguish session-only state from host persistence.
- Distinguish requested action from completed connection.
- Explain exact remembered permission scope.
- Provide host-rule revocation.
- Populate TUI actions from daemon inventory.
- Hide inapplicable actions and name their subjects accessibly.

## Phase 3 — Build progressive discovery once

Add daemon/SDK-backed:

- Paged per-server listing.
- Cross-server lexical search.
- Exact tool description.
- Instructions, provenance, and authorization display.
- Optional generated TypeScript guidance.

Reuse it for both model discovery and product inspection, while preserving caller-specific visibility and authority.

## Phase 4 — Preserve MCP results

Introduce a bounded typed result model that retains:

- Text.
- Structured content.
- Application error state.
- Image/resource references.
- Relevant metadata.

Render and inspect that model in clients. Do not try to fix discarded images with a frontend-only card.

## Phase 5 — Complete setup and authentication

Then add:

- Persistent add/edit/remove.
- Import preview and source/conflict explanation.
- Explicit startup authorization.
- Safe connection diagnostics.
- OAuth where supported.
- Account/credential ownership and reauthentication.
- Schema-driven manual testing.

Keep all execution and credentials on the daemon side.

## Phase 6 — Only if the product direction warrants it

Consider:

- A broader integration/connection abstraction.
- OpenAPI/GraphQL adapters.
- Aggregate outward MCP.
- Observed output schemas.
- Interactive tool-backed artifacts.

These are plausible opportunities, not prerequisites for making Whip’s current MCP experience good.

# 12. Questions that should shape the next decision

The findings above do not depend on answers, but the architecture beyond the repairs does:

1. **Should MCP be a first-class host-level integration destination, or remain primarily session configuration?**  
   The current UI is session-centered, while credentials and imports are often host-scoped.

2. **Is `definition.mcp.servers` intended as a security boundary or just a startup selection?**  
   Its documented semantics suggest restriction. I recommend making that restriction invariant across runtime changes.

3. **What should enabling an import source authorize?**  
   Discovery only, or arbitrary future startup execution from matching project configs? I recommend separate discovery and connect/spawn authorization.

4. **Who is the first-class setup user: config-editing developers, nontechnical users, or both?**  
   This determines whether CLI guidance is enough temporarily or a setup wizard/OAuth flow is urgent.

5. **Are multiple accounts and shared/team daemons near-term requirements?**  
   If yes, credential ownership and integration-versus-connection identity should come before proliferating convenience APIs.

6. **Should `whip mcp serve` remain a small utility bridge, or become a way for other agents to use Whip’s integration catalog/runtime?**  
   Those are substantially different products and authority models.

7. **Which actual servers matter most to you?**  
   A representative set—stdio developer tool, static-token HTTP server, OAuth service, large paginated catalog, and image/structured-output tool—would provide a much better acceptance matrix than generic “MCP supported.”

## Bottom line

**Whip does not need a new MCP runtime. It needs its existing contracts repaired and a real integration experience built around them.**

Executor is the right reference for **discovering, understanding, connecting, and managing tools**. Whip’s own architecture is the stronger foundation for **durable agent execution, delegated authority, and consent that the model cannot grant itself**.
